# 最终独立意见（只读、限时）

## 1. 小修复是否合理
合理。`request_permissions` 的两处回显改为 `strip_internal_context(effective_args.clone())`，只移除顶层 `_host_session_key` 与 `_active_project_root`，不改权限判定、不动嵌套用户参数，属于最小面、低风险的内部键泄漏修复。两点必须说清：
- 它**不修复**本次六条红探针中的任何一条，二者是不同问题，不能据此宣称回归已解决；
- 修复前的两条失败与它相关，但"修复后测试进行中"目前**无证据**，不能视为已验证。

## 2. HOLD 是否被观测证据支持
支持。stderr.log 中六条独立安全期望探针全部失败，且失败均为**行为缺陷**而非断言写法问题：
1. 损坏绑定库 → 重绑他会话 → 第二次重启后旧会话按 `default_cwd` 静默回落（`source=default_cwd`）；
2. 两个上下文顺序写入整张 map，后者覆盖前者（丢更新）；
3. `history_dir=src` 使真实代码被排除出 Harness 基线，`pwd` 仍成功执行；
4. 只读 History 搜索因元数据不可写而失败（`MANAGED_PROJECT_PATH_STORE_UNAVAILABLE`, os error 183）；
5. 根 Active Project 自定义 History 排除失效，基线被写操作污染（`FILE_CHANGED_EXTERNALLY`）；
6. 池内符号链接替换后读取到 `beta` 而非原 `alpha`。
"无静默跨项目回落""History 记账不得削弱真实代码检查"正是设计红线，第 1、3、5 条直接违反，因此暂缓 .5 线上验收、保留小修复在本地审计分支、不推不合并是恰当的保守选择。

## 3. 需要指出的夸大/边界
- **两个 ToolContext ≠ 同一共享上下文里的两个会话**：探针是顺序写入而非并发，生产若为"一 Connector + 单上下文"则多写者概率下降；但整表覆盖的丢更新模式真实存在，多进程/多实例共享同一 store 时仍会触发。
- **第 6 条需要本地文件系统改动**（替换符号链接）才能复现：绑定校验在绑定时刻 canonicalize，后续再次解析，属本地写权限前提下的重定向，不是纯远端场景。
- **第 4 条的 os error 183** 指向 Windows 上 rename 目标已存在/元数据写入路径，不应据此直接下结论为"设计必然要写盘"，但"只读搜索却要求写权限"的耦合成立。
- 我**无法直接核实 History 源码**：本任务只给了日志，未读 `history.rs`，第 3、4 条仅凭日志断言，需主 agent 复现确认。
- 首任 advisor 的文件搜索超时，其运行**不得**记为成功，也不得据此宣称全仓库已审计。

## 4. 需用户批准的较大变更
持久化恢复/隔离 + 共享 store 事务化写入；History 目录归属与只读分离 + 根作用域一致性；拒绝被篡改的规范绑定目标。不建议重型 DB，也不建议每项目新建 Connector。
